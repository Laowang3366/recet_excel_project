# ExcelCC 项目开发规范

本文档用于指导 ExcelCC 后续维护、重构和功能扩展。目标是让项目继续保持做题、教程、模板、QA 与 AI 助手平台的清晰边界，避免代码再次膨胀、职责混乱或引入不必要的安全风险。

## 1. 基本原则
- 目标是“让项目更清晰、更可维护、更可测试”，不是单纯把代码拆碎。
- 重构优先考虑稳定性、职责边界与可理解性。
- 任何新增功能都必须沿现有分层接入，禁止重新堆回大文件。
- 乱码问题视为阻塞问题，不是“后面再顺手修”的小问题。
- 先明确业务边界，再写代码。新增功能必须能归入当前产品模块：做题、教程、模板、QA、AI 助手、通知、后台管理、文件管理、用户与单位。
- 保持单一职责。页面、组件、Controller、Service、Mapper 都只处理自己的职责，不把多个业务流程塞进一个文件。
- 优先兼容线上数据。禁止修改历史 Flyway migration，数据库变更必须新增 migration。
- 先收口风险，再重构结构。涉及鉴权、奖励、上传、下载、Excel 解析、文件删除的改动必须先写清楚边界和验证方式。
- 避免过度设计。能用明确 DTO、Service 方法和简单条件判断解决的问题，不引入复杂设计模式。
- 任何线上部署必须走标准部署流程，并更新 `ONLINE_UPDATE_LOG.md`。

### 1.1 开发前必须实际阅读
- 任何涉及代码、流程、UI、步骤、配置、测试、文档、提交、合并、发布的任务，开始前必须实际阅读或重新核对：
 - [项目文件结构说明](./项目文件结构说明.md)：确认新增文件、模块拆分和文档归档位置。
 - [项目完整链路说明](./项目完整链路说明.md)：确认改动会影响的前端、后端、数据库、文件、通知、AI 和部署链路。
 - [部署与运维说明](./deployment-operations.md)：涉及线上发布、服务器目录或部署脚本时必须阅读。
 - [发布检查清单](./maintenance/release-checklist.md)：上线前按清单逐项验证。
 - 当前文件
- 不能只凭历史记忆、上一次会话摘要或“看起来知道项目”直接开发。
- 如果用户指出“先分析”“只分析”“暂时不改”，只能输出分析，不得擅自改代码或提交。
- 如果用户要求“开始开发”“按照清单开发”“提交代码”，必须按阶段推进到完成，不能停在方案层。


## 2. 仓库与模块边界

### 后端

后端目录为 `excel-forum-backend/`，包名统一在 `com.excel.forum` 下。

各模块职责：

- `controller`：只接收请求、校验认证上下文、调用 Service、返回响应。
- `service`：承载业务规则、事务、幂等、限流、文件流转等核心逻辑。
- `mapper`：只做数据库访问，不写业务判断。
- `entity`：映射数据库表，不混入请求或响应语义。
- `config`：跨模块配置，如 Web、Security、CORS、定时任务。
- `security`：认证、授权、JWT、登录风控。
- `util`：无状态、低依赖工具函数。业务工具优先放到对应 Service。

禁止继续膨胀单个大 Controller。后台新增模块时应优先建立独立 Controller，例如 `AdminQaController`、`AdminFileRecycleController`，保持 `/api/admin/**` 路径兼容即可。

### 前端

前端目录为 `reace_web/`，应用代码在 `src/app/`。

各模块职责：

- `pages`：路由页面，负责页面级数据装配和布局。
- `components`：可复用 UI 与业务组件。
- `admin`：后台管理页面和后台专用组件。
- `lib`：API 封装、Excel 工具、格式化、权限判断、纯函数。
- `routes.tsx`：只维护路由关系，不写业务逻辑。

页面文件不应长期超过可读范围。若页面同时处理列表、表单、弹窗、上传、权限和状态同步，应拆成组件和 hooks。

## 3. 后端开发规范

### API 与 DTO

- 请求体必须使用明确 DTO，不使用 `Map<String, Object>` 承载业务输入。
- DTO 要用 Bean Validation 标注字段范围、长度、枚举值和必填项。
- 对外响应禁止返回实体对象原样内容，必须通过响应 DTO 控制字段。
- 管理员接口必须显式校验角色，不依赖前端隐藏按钮。
- 普通用户接口必须校验资源归属，例如答题记录、QA 求助、模板下载权限。

### Service 与事务

- 写操作必须在 Service 层处理事务边界。
- 积分、经验、奖励、下载次数、答题状态等计数必须具备幂等设计。
- 用户可重复操作的接口要考虑并发：重复提交、重复点击、脚本请求、网络重试。
- 删除文件型业务记录必须走文件回收站策略，不直接物理删除上传文件。

### 数据库

- 所有结构变更新增 Flyway migration，禁止编辑历史 migration。
- 自增 ID 不重排、不复用、不递减。
- 查询列表默认过滤软删除数据。
- 新增索引前要确认查询路径和数据规模，避免无意义索引。
- 批量更新和批量删除必须限制输入数量，防止大事务拖垮数据库。

### 文件、上传与下载

- Excel、图片、附件上传必须校验大小、扩展名、MIME、文件签名和 workbook 复杂度。
- 敏感 Excel 文件不直接暴露 raw URL，优先通过业务 ID 下载或预览。
- 下载接口必须限流，并校验用户是否有权访问对应业务文件。
- 删除上传文件必须进入文件回收站，保留期按当前策略执行。

### 安全

- 登录、注册、找回密码、AI、上传、下载、答题提交必须接入限流。
- 错误响应不暴露堆栈、SQL、文件绝对路径、密钥或内部配置。
- JWT、数据库、Redis、MinIO 等凭据只能通过环境变量或服务器配置注入。
- 生产环境必须关闭 debug，数据库和 Redis 不允许裸露公网。
- 用户提交的文本、昵称、答案、Excel 内容导出时要防 CSV/Excel 公式注入。

## 4. 前端开发规范

### 数据访问

- API 调用统一放在 `src/app/lib` 或就近业务 API 文件中，不在 JSX 中拼复杂请求。
- React Query key 要按业务模块命名，禁止残留已下线模块命名。
- mutation 成功后只刷新相关 query，不做全局无差别刷新。
- 前端只能做体验控制，权限、安全、判题、奖励必须以后端结果为准。

### 页面与组件

- 页面负责“取数、路由、状态协调”，组件负责“展示和局部交互”。
- 弹窗、上传、编辑器、表格、筛选器应独立组件化。
- 后台列表必须提供筛选、分页或折叠策略，避免数据一多就难以操作。
- 所有可编辑列表应有明确的批量选择、批量删除或批量状态操作边界。

### UI 与交互

- 保持 ExcelCC 当前绿色系和学习工具感，不做花哨营销页。
- 按钮文案描述业务动作，不把开发逻辑或内部约束写给用户。
- 失败提示要说明用户能做什么，例如重新上传、刷新、稍后再试、联系管理员。
- 通知、登录跳转、答题返回等流程必须保留原始来源页面，不默认回首页。

## 5. Excel 编辑器与题目规范

Excel 编辑器是在线答题和模板配置工具，不是完整 Excel 365/WPS 计算引擎。维护时必须坚持两条边界：

1. 在线编辑器负责输入、预览、区域选择、格式设置和轻量计算。
2. 复杂动态数组公式必须保留公式锚点和答案快照，不能用缓存子单元格覆盖公式溢出结果。

题目与模板相关改动必须特别注意：

- 上传模板后不得丢失原始工作表、公式、日期格式、文本格式和空白结构。
- 动态数组公式只保存锚点公式，溢出子区域不得作为普通用户输入值挡住溢出。
- 日期要保留 Excel serial、显示格式和前端展示值之间的转换关系。
- 保存题目时，题目要求不能泄露标准答案、答案解析或判题明细。
- 前端答题页不得一次性返回标准答案、解析或隐藏字段。
- 管理后台可见的标准答案和规则必须和前端用户态数据分离。

凡是修改 Excel 序列化、导入、导出、判题、动态数组、日期格式、删除键、Esc 行为，都要补对应前端测试或最小复现用例。

## 6. QA、做题、模板与 AI 模块边界

- 做题模块只负责题目读取、作答、判题、进度、奖励和结果展示。
- QA 模块只负责案例求助、答疑文件、解题分享和答疑通知，不扩展成评论、私信、帖子或社区流。
- 模板中心只负责模板展示、购买/下载、预览和后台维护。
- AI 助手只负责对话、附件识别、后台模型配置和调用统计，不承载业务权限判断。
- 通知模块只负责通知创建、读取、跳转和状态，不把业务流程写进通知组件。

跨模块调用要通过清晰的 Service 或 API，不共享隐式状态。

## 7. 重构规范

重构前先确认：

- 当前线上行为是什么。
- 哪些接口、路由、数据库表和文件不能破坏。
- 是否需要灰度、兼容字段或数据迁移。
- 是否有测试覆盖关键路径。

重构执行要求：

- 小步提交，保持每一步可构建、可回滚。
- 不顺手修改无关文件。
- 不为了清理命名而改变对外 API。
- 大组件拆分时先抽纯展示组件，再抽业务 hooks，最后再清理旧代码。
- 大 Controller 拆分时保持路径兼容，先搬方法和测试，再清理依赖。

## 8. 测试与质量门禁

常规验证命令：

```powershell
cd reace_web
npm run typecheck
npm run test
npm run build
```

```powershell
cd excel-forum-backend
mvn test
```

改动验证要求：

- 前端 UI 改动：至少通过 `typecheck`、`test`、`build`，关键页面需要浏览器验证。
- 后端接口改动：补 MockMvc 或 Service 测试，覆盖成功、鉴权失败、非法输入和边界条件。
- 数据库改动：新增 migration，并用测试或本地启动确认迁移可执行。
- 安全相关改动：验证未登录、普通用户、管理员三类身份。
- 上传/下载/Excel 改动：验证文件大小、非法文件、正常文件、重复操作和并发风险。

## 9. 部署与上线规范

生产更新前必须阅读：

- `docs/deployment-operations.md`
- `docs/maintenance/release-checklist.md`
- `ONLINE_UPDATE_LOG.md`

上线原则：

- 生产源码目录为 `/www/wwwroot/excelcc/kick-deploy/repo`。
- 使用标准部署脚本，不整目录覆盖线上项目。
- 不触碰 `/www/wwwroot/quick-translate` 等其他项目目录。
- 部署后验证首页、`/api/public/home-overview`、小试牛刀、教程、模板、QA、AI 助手等关键路径。
- 部署成功后在 `ONLINE_UPDATE_LOG.md` 顶部记录变更范围、验证命令、部署目标、备份路径和残余风险。

## 10. 新功能准入清单

新增功能进入开发前，至少确认：

- 属于哪个现有模块，是否会引入新的模块边界。
- 是否需要登录，是否区分普通用户、管理员、单位用户。
- 是否涉及文件、积分、经验、奖励、支付、AI 调用或通知。
- 是否需要限流、幂等、审计日志或回收站。
- 是否会向前端暴露答案、内部路径、隐藏字段或敏感配置。
- 是否需要数据库 migration，是否保留历史数据。
- 是否需要更新文档、后台入口、通知跳转或部署说明。

如果以上任一项不清楚，先补设计说明或任务拆分，不直接开始编码。

## 11. 代码评审重点

评审时优先看风险，不只看风格：

- 是否存在越权访问、未校验资源归属、前端假鉴权。
- 是否存在重复奖励、重复提交、重复下载、重复删除。
- 是否把答案、解析、隐藏字段提前返回给用户。
- 是否可能上传大文件、复杂 workbook 或恶意公式拖垮服务。
- 是否存在 SQL 注入、XSS、CSRF、CSV/Excel 公式注入。
- 是否有大组件、大 Controller、大 Service 继续膨胀。
- 是否有未使用变量、未使用导入、重复代码或旧模块命名残留。
- 是否缺少边界测试、异常处理或线上回滚路径。

## 12. 文档维护

- 根目录只保留高频入口文档，新增长期文档优先放入 `docs/`。
- 一次性计划、过期审计和历史方案放入 `docs/archive/`。
- 运维流程放入 `docs/maintenance/` 或 `docs/deployment-operations.md`。
- 安全审计和风险修复记录放入 `docs/security/`。
- 文档中不要记录密码、密钥、Token、服务器凭据或数据库连接串。
